# 起点对比交互与接口需求

2026-11-17 · 前端组评审稿。

2026-11-23 实现更新：三页签与起点对比已完成。正式接口已采用 `POST /api/routes`（loop/oneway，1–42 km）和 `GET /api/toilets`（accessible），以现行接口契约为准。下面保留最初设计提案供追溯。
现有接口以 [接口契约 v1.2](接口契约.md) 为准。本稿中的新增接口和字段由前后端评审后纳入正式契约。

## 1. 起点对比（FR-33）

用户在相同路线条件下比较两个起点各自的最佳环线。首版沿用现有 3、5、10 km 距离档和绿荫、安全、平坦偏好。

```text
路线推荐   起点对比
┌──────────────────┬─────────────────────────┬────────────────────┐
│ A 选择起点        │                         │ 指标       A    B   │
│ B 选择起点        │    武汉地图             │ 偏好匹配分          │
│                  │    A  ● ━━━ 环线       │ 实际距离            │
│ 共同距离 3 / 5 / 10 │    B  ◆ ┄┄┄ 环线       │ 预计用时            │
│ 绿荫 / 安全 / 平坦 │                         │ 树冠 / 坡度 / 设施   │
│ 比较路线          │                         │ 起点吸附偏差         │
└──────────────────┴─────────────────────────┴────────────────────┘
```

- 顶部「起点对比」进入独立视图。A 默认带入推荐页当前起点，B 留空。点击 A 或 B 的「地图选点」后，下一次地图点击只更新该栏。两栏均可复用预设地点和地图选点。选到相同坐标时提示用户换一个地点。
- 距离和偏好只设一份。点击「比较路线」时保存本次输入，分别计算 A、B。地图用 A/B 标签和实线、虚线区分，成功后让两条路线都进入视野。窄屏按条件、地图、对比表顺序排布，表格仍保留 A/B 两列。
- 每侧取自己的 `rank = 1`。表格展示偏好匹配分、实际距离、预计用时、树冠比例、平均坡度、设施距离指标和吸附偏差。安全、绿化、坡度三个子分可展开查看；只有双侧都有值时才显示差值。树冠差以百分点展示，两侧同分时显示相同分值。设施行沿用现有 `facility_m` 的统计口径。
- 两侧独立呈现「计算中」「成功」「无路线」「请求失败」。一侧无路线时保留另一侧，提示换该侧起点或共同距离。请求失败可按本次条件重试该侧。两侧均成功才做分数比较。吸附偏差大于 100 m 给提示；是否判定起点无效由后端规则决定。
- 条件改变时清除这次对比结果，丢弃过期响应。回到路线推荐页继续原来的单起点操作。

### 1.1 首版直接复用 `POST /api/loops`

点击一次「比较路线」，提交下列两个请求。前端按请求所属栏位记录 A/B，响应先后不影响展示。两次请求必须使用相同的 `target_m`、`prefs`、`max_candidates`。

```json
{"lng":114.3547,"lat":30.5342,"target_m":5000,"prefs":{"green":1,"safe":1,"flat":0.6},"max_candidates":8}
```

```json
{"lng":114.3416,"lat":30.5526,"target_m":5000,"prefs":{"green":1,"safe":1,"flat":0.6},"max_candidates":8}
```

接口与单点推荐使用同一算法、路网数据与排序规则。返回 GeoJSON FeatureCollection，几何为闭合 LineString，坐标统一 WGS84 `[lng, lat]`。已有字段 `length_m`、`minutes`、`score`、`tree_share`、`slope_mean_pct`、`facility_m`、`origin_snap_m`、`sub`、`rank` 足够支持首版。`sub` 是 JSON 字符串。 `tree_share` 为 0–1，`slope_mean_pct` 已经是百分数，`score` 为路线偏好匹配分。

| 单侧响应 | 前端显示 |
|---|---|
| 200，存在 `rank = 1` | 渲染该侧路线和指标 |
| 200，`features: []`，带 `message` | 显示该侧无路线及调整建议 |
| 422 | 提示检查坐标或路线条件 |
| 503 | 提示路线数据暂不可用，可重试 |
| 500、网络错误或超时 | 提示该侧计算失败，可重试 |

请后端确认两个请求并发时的响应时间和资源占用，以及服务是否能区分「起点无效」和「起点有效但无合适路线」。若能区分，建议为 200 空结果增加可选 `reason` 枚举 `invalid_origin` / `no_route`，保留现有 `message` 和 `features`。首版可以用现有响应做通用空态。若联调发现并发开销明显，再评审是否做服务端双起点批量计算。

## 2. 单行线与路段详情

| 功能 | 前端操作 | 接口对接 |
|---|---|---|
| 单行线 | 选择「单行线 A→B」，用户给起点和距离，系统选终点。切换候选时同步更新终点标记和指标。 | **提案** `POST /api/oneway`。请求与 `/api/loops` 相同，响应沿用 FeatureCollection 和路线属性，几何首尾必须不同，第一个点为吸附后的起点，最后一个点为终点。沿用空结果和错误约定。首版请求范围与环线保持 1–20 km，需求的 42 km 上限另请后端确认。 |
| 路段详情 | 地图工具栏在「选起点」「查路段」之间切换。查路段时点击高亮，详情显示路段综合分、等级、六个子分、原始指标及数据说明。 | **已有** `GET /api/segments/{osm_id}` 返回完整 Feature。评分图层要保留可用于查询的 `osm_id`。权重、数据说明读 `GET /api/meta`。若同一 `osm_id` 对应多段，请后端确认能唯一定位的标识及详情查询方式。 |

路段详情与图例采用同一数据版本和分档。需求表 11 的分界是 45、50、65、80，当前评分脚本第一道分界为 35。请数据组和后端确认正式分档、边界归属及新版 Web 路网产物，再刷新静态快照与评分图例。

## 3. 洗手间筛选与热点

- **洗手间（FR-07）**。将原「洗手间 / 补给点」改成地图的「洗手间」筛选。开启后在当前视野显示公厕点，点击显示名称和可用地址。点位请求失败时只提示图层问题。此开关只影响展示。
- **洗手间接口提案**。在 `GET /api/pois` 增加 `kinds=toilet`，复用 `min_lng / min_lat / max_lng / max_lat` 和 `limit`。返回 WGS84 Point FeatureCollection，沿用 `total`、`truncated`、`kinds`、`exclude_leisure` 和 `bbox` 字段。每点返回字符串 `poi_id`、`name`、`kind: "toilet"`，以及可为 null 的 `address`。建议首版读取 `poi.gpkg` 中公开可用的 `fclass=toilet`，室内点另议。请确认稳定 ID、去重口径及缺失名称、地址的表示。现有 `sport` 和 `all` 行为按 v1.2 保持兼容，厕所通过显式筛选取用。
- **热点（FR-34）**。沿用全城视野的「推荐热点」静态图层，点击点位显示离线样本的最佳分和有效候选数，并提供「设为对比起点」入口。验收前需在数据说明中标出离线计算的目标距离、偏好和数据版本。用户点击「比较路线」后按当次条件重新计算。

## 4. 联调与验收

| 用例 | 通过条件 |
|---|---|
| A、B 均有环线 | 两侧实际提交条件一致。各侧显示自己的首选路线，地图样式、起点和指标对应。 |
| A 有环线，B 无路线或失败 | A 仍可查看。B 显示对应提示，无双侧差值。失败侧可按原输入重试。 |
| A、B 请求逆序返回或计算中改条件 | 结果仍归正确栏位。旧条件的响应不会覆盖新页面。 |
| 单行线切换候选 | 首尾不同，地图终点和结果指标随候选更新。 |
| 查看路段及切换洗手间 | 详情与点击路段及地图等级一致。点层筛选和路段详情均不触发路线重新计算。 |

前端可以先按现有环线响应制作对比 mock，覆盖双成功、单侧无结果、单侧失败和响应逆序。后端评审时请确认环线双请求负载、单行线返回语义、厕所 POI 字段及路段标识。双方确认后，把新增接口写入正式契约的变更记录，再按同一组样例联调。
