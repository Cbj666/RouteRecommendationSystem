# 分工卡片

更新日期：2026-11-17
用途：**把工作嵌进四层架构**——每份工作都对应"读哪一层、写哪一层"，不是记流水账。
负责人一栏由组长填姓名。

> **进度注记（2026-11-17）**：接口层已完成并实测（11 个路由，见 `docs/接口契约.md` v1.2），
> 前端不需要再等契约；下表保留原分工，凡写“5 个端点”均按 11 个接口理解。
> 剩余主要是 Vue 页面、地图层与部署加固。

**已定**：后端用 **Python（FastAPI）**，单进程单端口；不做 Java 网关，也不引入 gRPC。

## 一、总览：七个人，三个组

```text
前端组（2 人）   表现层 + 接口契约 ──┐ 可点击、无真实后端（mock）
                                   ├─ 契约冻结后并行
后端组（3 人）   接口层 + 算法层 ────┘ 真实数据、真实算法（Python / FastAPI）
热点分析（1 人） 算法层·空间分析，从第 1 周就开跑
组长（1 人）     数据层 + 文档与答辩
```

**关键顺序**：前端组先交付**接口契约 + 可点的前端骨架**；契约一冻结，后端组立刻并行开工，
**不要等前端全部做完**——否则后端组会空转一到两周。

## 三、后端组的形态

```text
浏览器 ──HTTP/JSON──> FastAPI 进程（uvicorn，单进程单端口）
                        ├── 校验 / 缓存 / 错误码 / CORS
                        ├── 静态托管前端构建产物（生产环境，同源无 CORS）
                        └── 直接 import running.py ──> 内存里的图与算法
```


| 项              | 内容                                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------- |
| 技术栈          | FastAPI + pydantic + numpy/scipy                                                                           |
| 启动            | `uvicorn app.api:app --app-dir backend --port 8000`                                                        |
| 数据            | 无数据库；启动时把`run_graph.npz`（37 MB）读进内存，0.4 s                                                  |
| 规模            | worker 1–2 个（每个 worker 各载一份图），靠缓存而不是加机器                                               |
| 为什么不用 Java | 图缓存是 numpy 的`.npz`、算法是 `scipy.sparse`；用 Java 复现既费时又必然和报告数字（0.2 s、78.5 分）对不上 |

**后端组的三个交付物**：能跑的 11 个接口（带缓存与错误码）、一份 `docs/接口契约.md` 的实现确认、一份压测记录。

## 四、为什么要先定契约

后端组三个人要同时改 `api.py`，如果各写各的，合并时必然打架。两条硬规则：

1. **契约只有一个人签字**：`docs/接口契约.md` 由前端组 A 维护，其余人只读；
2. **mock 与实现同源**：`frontend/app/src/api/mock/*.json` 直接从契约里的样例拷过去，
   前端不猜字段名，后端不猜前端要什么。

这样做，前端组交付的那一版"能点但没数据"的页面，就是后端组的验收基准：
**接口一接上，页面不用改一行代码就应该能跑**。

## 五、串行 vs 并行的取舍


| 做法                                 | 优点                                     | 风险                                             |
| ------------------------------------ | ---------------------------------------- | ------------------------------------------------ |
| 完全串行（前端全部做完 → 后端开工） | 责任清晰、不用联调                       | 后端组空转 1–2 周；前端等到最后才发现接口不够用 |
| 契约先行、两组并行（建议）           | 后端组第一周就能开工；联调只发生在契约层 | 需要有人先花 2–3 天把契约写死                   |

结论：**先花 2–3 天冻结契约，再两组并行**，比"前端做完交后端"快一到两周。

## 七、协作约定

### 7.1 分支与提交

```text
main                    只收合并，由组长合
feat/frontend-xxx       前端组
feat/api-xxx            后端组·接口
feat/algo-xxx           后端组·算法 / 热点分析
docs/xxx                文档
```

提交信息：`feat(frontend): 接入百度底图`、`fix(api): 修复 bbox 越界`。
**不要直接改别人的层**；改跨层公共代码（`running.py`、`api.py`）先在 `docs/接口契约.md` 里登记。

### 7.2 完成定义（DoD）

- [ ]  有代码 / 文档 / 图，且别人能按说明跑出来；
- [ ]  产出写在约定的路径（见上表「产出写到哪里」），不散落在桌面；
- [ ]  跨层改动在契约文件里有记录；
- [ ]  提交信息能追溯到人。

## 八、不要再做的事（避免返工）

1. **不要重新抓高德数据**：场馆缓存、AQICN 缓存、CHAP netCDF 都在本地；
2. **不要重写评分体系**：当前六维与权重就是答辩口径，改了就得多解释一遍；
3. **不要用别的语言重写算法**：图缓存是 numpy 的 `.npz`，重写必然与报告数字对不上；
4. **不要动等时圈代码**：`graph.py` / `isochrone.py` 只作历史资产；
5. **不要改目录结构**：路径已收敛到 `app/paths.py` 与 `scripts/_paths.py`；
6. **不要在 `data/processed/running/` 里手工改文件**：重跑脚本会覆盖；
7. **不要引用没核对过的文献**：`docs/literature/参考文献.md` 里标了「限制」的条目不要当依据。
